# Глухота плат EC4: детект затыка микрофона и самолечение (Фаза 2, октябрь 2026)

## Симптом

Плата EC4 (ESP32 + CX20921) перестаёт реагировать на wake word: LED-кольцо в
режиме прослушивания, но аудио от микрофона в HA не поступает. Перезагрузка
по питанию лечит. До фикса единственной защитой была ночная перезагрузка
всех плат в 05:00 и ручное вмешательство.

## Корневая причина

Драйвер микрофона (`cx_i2s`) зависает: задача чтения I2S перестаёт возвращать
данные, `va_dsp_init` при этом уже выполнен — повторная инициализация в рантайме
не чинит DSP (см. «Неидемпотентность va_dsp_init»). Помогает только сброс
чипа.

## Фаза 1 — watchdog в HA (коммит `50906e910dc`)

В `esphome/assist_satellite.py`: таймаут 3с без аудио при активном прогоне →
форс-реконнект API-сессии платы. Лечит случаи, когда зависала не прошивка,
а «зомби-сессия» HA (см. docs/fleet-audit-2026-10.md). Работает только если
плате хватает реконнекта, мёртвый I2S не спасает.

## Фаза 2 — детектор в прошивке (esphome-cx-audio-2026.7.4, main @ `803ee0e`)

Ветка `fix/mic-stall-recovery`, три коммита (`2d456a7` → `b1cc7b4` → `803ee0e`).

### cx_i2s.h

- `set_simulate_stall(bool)` — тестовый хук для симуляции затыка
- `MIC_STALL_TIMEOUT_MS = 2000` — порог тишины данных
- `MIC_STALL_MAX_RECOVERIES = 3` — попыток до эскалации

### cx_i2s.cpp

- `recover_dsp_()` — GPIO21 (reset DSP) pulse 100/500мс + `va_dsp_init` +
  восстановление gain
- Детектор в read_loop: есть данные → сброс счётчиков; 2с без данных при
  работающем микрофоне → `recover_dsp_()`, до 3 попыток
- После 3 неудач → `esp_restart()`. Перед рестартом `vTaskDelay(250)` —
  иначе строка «rebooting» не успевает уйти в лог (API-сокет умирает раньше)
- Симуляция (`simulate_stall_`) пропускает только `i2s_read` (err=ESP_OK,
  bytes_read=0) — затык идёт через **настоящий** детектор, путь проверки
  идентичен боевому (первая реализация с ранним `return 0` обходила детектор
  — симулировала ничего, тест был зелёным впустую)

### Итоговый цикл самолечения

```
затык → +2.0с recover 1/3 → +2.0с recover 2/3 → +2.0с recover 3/3
      → строка "rebooting" → esp_restart → ~8с до загрузки → mww работает
Всё с момента затыка ≈ 30с (verify: recoveries на t+2.1/4.1/6.1с от старта)
```

## Неидемпотентность va_dsp_init

Повторный вызов на живой прошивке:

```
gpio_install_isr_service: already installed
rb_adapter: Failed to allocate rb buffer: size=70400 (free=…)
CX20921: Failed to allocate audio buffer
```

Рантайм-`recover_dsp_()` частично освобождает/переинициализирует, но полностью
DSP не поднимает — поэтому эскалация ребутом это не «запасной», а основной
механизм лечения. Проверено на тест-плате: после 3 recoveries ребут поднимает
плату полностью (Peak-сенсор живой, −24.4 дБ, затыков 0).

## Верификация (тест-плата ec4-test-board @ 192.168.0.115, сборка 13:30:08)

1. Свич `Simulate Mic Stall` ON → лог: stall detected → recovery 1/3, 2/3, 3/3
   ровно каждые 2с
2. Строка `rebooting` видна в логах (до фикса задержки — терялась)
3. После ребута: плата отвечает, свич OFF, симуляция чистая
4. E2E подтверждён вручную: «работает, отвечает»

Прошивка OTA с ПК: docker `python:3.14-slim` + `pip install` git-archive форка
(`fork-src.tar.gz`) + скрипт с `run_ota(ip, 3232, password, path)`.
`espota.py` отдельным скриптом не существует — `espota2.py` это модуль пакета.
